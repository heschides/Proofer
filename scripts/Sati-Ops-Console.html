1. Every new PowerShell window

Two things a fresh window doesn't have. You'll do these constantly.

Point the window at the repo

Scripts are referenced by relative path (.\scripts\…), so PowerShell has to be sitting in the repo folder or it won't find them.

cd C:\Users\SatiLogica\source\repos\heschides\Sati

Allow scripts to run in this window

Windows blocks .ps1 files by default — a safety default on every fresh install, not anything about these scripts. -Scope Process means the permission applies only to this window and evaporates when you close it, so you're not changing a system setting.

Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass

Silent, or a Y/N prompt — answer Y.

Tired of retyping it? Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned makes it permanent for your account, allowing local scripts while still blocking unsigned ones downloaded from the internet. That one is a real security setting change, so it's a deliberate choice rather than a convenience.

2. Check state before you change anything

Cheap, read-only, and answers "do I even need to do this?"

Is the Azure database awake?

SatiDemo is a serverless database. That doesn't mean there's no server — it means Azure powers the compute down when nobody's connected and powers it back up on demand, so you pay per second used instead of renting a machine that idles. While it's waking, connections are refused with "Database is not currently available."

az sql db show --name SatiDemo --server sati-demo-satilogica-central --resource-group rg-sati-demo --query status -o tsv

Online = ready. Paused = asleep; the next connection attempt wakes it (and usually fails while doing so).

Two different kinds of paused. Ordinary idle-pause wakes in 30–60 seconds — just retry. But your database is on the free monthly allowance with a cost guard that pauses it for the rest of the billing month once that allowance is spent. If retrying never works and status stays Paused, that's which one you've hit, and waiting won't fix it.

Does a database already have the SSN columns?

Tells you whether the migration has landed, without changing anything. Swap the -d value to check a different database.

sqlcmd -S "(localdb)\MSSQLLocalDB" -d SatiProduction -Q "SET NOCOUNT ON; SELECT name FROM sys.columns WHERE object_id = OBJECT_ID('dbo.People') AND name LIKE 'Ssn%' ORDER BY name;"

Six rows — SsnCiphertext, SsnKeyId, SsnLastFour, SsnNonce, SsnTag, SsnWrappedKey. Zero rows means the migration hasn't been applied.

Is the hosted API healthy?

The readiness check compares the API's expected schema against the real database and names any missing column. It's the fastest way to confirm a migration actually took, and the first place a "database is behind the code" problem shows up.

curl.exe https://sati-demo-api-satilogica.azurewebsites.net/health/ready

HTTP 200. If it names a column, that column is missing from SatiDemo.

Use curl.exe, not curl. In PowerShell, bare curl is an alias for Invoke-WebRequest, which takes completely different flags — that mismatch is what left an earlier command sitting at a "Supply values for the following parameters: Uri" prompt.

3. Applying a migration

A migration is a schema change that already exists as a file in the repo. You are applying it, never creating it.

Local Production — one command, no ceremony

LocalDB runs on this laptop. No network, no token, no firewall, never asleep. The script defaults to (localdb)\MSSQLLocalDB so there's nothing else to pass.

.\scripts\Apply-SsnMigration.ps1 -DatabaseName SatiProduction

A small table: ColumnsAdded 6, HistoryRowWritten True. Running it again gives ColumnsAdded 0 — that's success, not failure. The script is safe to repeat.

Azure Demo — step A: let your laptop through the firewall

SatiDemo's firewall allows three App Service addresses and nothing else. Your home IP isn't on that list, and it changes, so the rule is created fresh each time and removed afterwards.

$ip = Invoke-RestMethod https://api.ipify.org
az sql server firewall-rule create --resource-group rg-sati-demo --server sati-demo-satilogica-central --name temp-laptop --start-ip-address $ip --end-ip-address $ip

A JSON blob describing the rule. If it says the rule already exists, you left one behind — that's fine, skip ahead.

Azure Demo — step B: get a database token

The server is Entra-only: no passwords. This mints a short-lived token proving you're you. It's your admin identity, not the API's — the API's managed identity is intentionally read/write only and cannot alter the schema.

$token = (az account get-access-token --resource https://database.windows.net --query accessToken -o tsv)

No output. The token is now in $token and lives only in this window.

Azure Demo — step C: apply it

Same script as local, pointed at Azure with the token.

.\scripts\Apply-SsnMigration.ps1 -DatabaseName SatiDemo -SqlServer sati-demo-satilogica-central.database.windows.net -AccessToken $token

ColumnsAdded 6, EnvironmentName Demo.

"Database 'SatiDemo' is not currently available" is the serverless wake-up, not a failure. Your attempt is what triggers the resume. Wait about a minute and run the same line again.

Azure Demo — step D: close the door behind you

The temporary rule is a hole in the firewall. Removing it is the established practice from the earlier deployments, and it costs nothing to redo next time.

az sql server firewall-rule delete --resource-group rg-sati-demo --server sati-demo-satilogica-central --name temp-laptop
Why a custom script instead of Entity Framework's own updater? SatiDemo and SatiProduction have picked up columns outside the normal migration chain over time, so EF's record of what's been applied disagrees with the actual schema in both directions. EF only consults its record, so it tries to add columns that already exist and fails. This script checks the real schema column by column and reconciles the record separately — which is also why re-running it is harmless.

4. Key Vault — one-time, per environment

Needed only to store an SSN. Forms still generate without it; the SSN box just prints blank and the result says so.

Create the vault and a key

The key never leaves Azure. Sati never sees it — it hands the vault a small per-record key to wrap, and asks for it back to unwrap. RSA is required because the code wraps with RSA-OAEP-256.

az keyvault create --name sati-demo-kv --resource-group rg-sati-demo --location centralus
az keyvault key create --vault-name sati-demo-kv --name ssn-demo --kty RSA --size 3072

Let the API use the key — and only use it

Two permissions: wrap and unwrap. Not read, not export, not delete. A compromised API can decrypt while it's running but can never walk away with the key itself.

az keyvault set-policy --name sati-demo-kv --object-id $(az webapp identity show --name sati-demo-api-satilogica --resource-group rg-sati-demo --query principalId -o tsv) --key-permissions wrapKey unwrapKey

Tell the API where the key is

Two details that look like typos but aren't. The double underscore is how App Service writes a nested config setting. The URL deliberately has no version on the end — that's what lets you rotate the key later without redeploying, because each stored row remembers which version encrypted it.

az webapp config appsettings set --name sati-demo-api-satilogica --resource-group rg-sati-demo --settings Ssn__KeyUri=https://sati-demo-kv.vault.azure.net/keys/ssn-demo

This restarts the API. Give it a minute, then re-check /health/ready.

Production gets its own vault and its own key — not a second key in the same vault. Separate keys mean Demo data is mathematically unreadable with the Production key and vice versa, so a connection string pointed at the wrong environment fails shut instead of quietly decrypting the wrong people's records.

5. Things not to do

Each of these looks reasonable and causes a mess.

Don't run Update-Database. It's the natural instinct in Visual Studio's Package Manager Console. On these two databases it fails with SQL error 2705 — "column already exists" — because EF's history and the real schema disagree. Use the script above instead.
Don't run Add-Migration for something that already exists. The migration file is already in the repo. Running Add-Migration would generate a second migration trying to add the same columns again.
Don't point a Demo command at Production or the reverse. The script refuses if the database's identity marker doesn't match the name you asked for — but that guard only works because you told it which environment you meant, so read the line before you run it.
Rebuilding fails while Sati is running. "The process cannot access the file… being used by another process" means the debugger still holds the DLLs. Stop debugging (Shift+F5) and rebuild.
